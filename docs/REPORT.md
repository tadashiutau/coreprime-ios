# Native text console, persistent PID 1, and real compatibility identity

Session 4, 2026-11-03. All phone boots in this session used `fastboot -s 45693dc9 boot` (RAM only). No partition was flashed, formatted, or restored. Kernel bytes remain Zcode's `cecca8a0a7b25cd59ee773c516346579f3a1be9ed3c6876a4ecafb405cd0d100`.

## Confirmed on the physical SM-G360T1

1. **Readable XNU text console on the panel.** The native loader now sets boot_args video.v_display=0, requesting text mode, and uses serial=0 for this diagnostic. The user independently saw Darwin text and PID 1 heartbeats at 5, 10, and 15 seconds. Full-resolution monochrome framebuffer captures taken before kernel entry and after return corroborate actual framebuffer changes.
2. **Persistent userspace without the deliberate PID1-exit panic.** The new standalone static Mach-O program `work/coreprime-xnu-loader/bringup.c` opens /dev/console, prints its PID/UID/version, and sleeps/wakes indefinitely with heartbeats every five seconds. The kernel's existing loader_return_after timer ends each diagnostic run without exiting PID 1. A 90-second native run produced heartbeats through 85 seconds, then the timer returned cleanly to lk2nd/fastboot; no panic appears in its harvested log. This is bounded diagnostic evidence, not a claim of indefinite stability.
3. **IPSW-derived compatibility identity.** DeviceTree.d22ap.im4p was extracted from the existing local iPhone X iOS 16.5/20F66 IPSW. Its IM4P OCTET STRING was LZFSE-decompressed and processed with upstream mkidentity.py. The native loader now emits the root/product/haptics/camera metadata. A corrected 45-second native run reports `hw.machine=iPhone10,3` and `hw.model=D22AP`, sends heartbeats through 40 seconds, and returns without panic. Identity metadata does not implement those Apple peripherals; CPU, GIC, timer, RAM, and framebuffer addresses still come from the Samsung's FDT.

## Diagnostic reliability fixes

The original generated identity_prop held `const char *name`. Those link-time absolute string pointers are wrong in a relocated freestanding loader. Its name field is now an inline `char name[32]`, generated by extract-identity.py after mkidentity.py. The build relocation guard previously used `llvm-readelf | grep -q` with pipefail; SIGPIPE could conceal a match. It now writes relocations to a file, then checks for ABS64. The current loader has no ABS64 C relocations.

Loader entry now clears only its own first 256 KiB ramoops dump region, preventing old kernel output/snapshots from surviving a pre-entry failure. It leaves lk2nd's console half at +0x40000 intact. The new phone runner checks the fresh loader log for an actual kernel return and rejects loader exceptions before accepting kernel text.

Two monochrome captures have CPFBMON1 headers at ramoops offsets 0x28000 and 0x34000; each is a 32-byte header plus 48,000 bytes for 480x800 pixels. Kernel log capacity is reduced to 0x24000 so it cannot overlap the captures. Capture happens before the loader draws over the returning kernel's screen. These are framebuffer-memory captures; direct human observation established panel visibility.

## Limits and next work

This is XNU plus our static syscall program, not a complete iOS installation. No Apple launchd/dyld/frameworks/SpringBoard have run in these tests. The boot memory window is still 0xa0000000+0x1ff80000; this is the current contiguous mapping, not an established permanent hardware ceiling. Swap is not functional: the kernel reports it cannot create its swap file.

Storage remains the next major requirement. Local lk2nd msm8916 source shows target_uninit deselects eMMC with CMD7, puts it to sleep with CMD5 (RCA=2), then disables SDHCI HC mode at core+0x78. A driver cannot assume a ready selected card at kernel entry. Existing HakiOS storage drivers cover UFS/virtio, not this MSM8916 SDHCI hardware. A retained-state, read-only loader probe is being tested separately; it is not yet a reusable XNU block driver or microSD driver.
